# ADR-017 · 남용 방지·데이터 보호: 여러 겹으로 막고, 막혀도 서비스는 멈추지 않게

| 항목 | 내용 |
|---|---|
| 상태 | **승인** — 결정권자 2026-11-10 |
| 관련 | ADR-015(장소 데이터·Google 비용) · ADR-016(익명 계정) · ADR-012 §4(비용·시간 상한, 정해진 순서 + 제한된 판단) · TASK-012 §10 Q4 · SRS NFR-12(동작 낮추기) |

## 1. 문제
서버를 인터넷에 올리면(파일럿) 주소를 아는 누구나 요청을 보낼 수 있다.
- **비용 공격**: 장소·숙소 검색은 우리 돈으로 Google을 부른다. 마구 부르면 비용이 늘고, 전체 상한을 걸면 **상한이 차는 순간 진짜 사용자도 못 쓴다**(상한이 공격 수단이 됨)
- **데이터 긁어 가기**: 장소 목록은 앞으로 수십 배로 늘고 머무는 시간·분위기 같은 **우리가 만든 값**이 쌓이는 자산이 된다. Google 값이 우리를 거쳐 새면 약관 문제도 생긴다
- **익명 계정의 한계**: 익명 로그인은 누구나 자동으로 할 수 있어서, IP를 바꿔 가며 계정을 새로 만들면 토큰만으로는 못 막는다. **완전히 막는 방법은 없다** → 비싸고 귀찮게 만들어 할 가치를 없앤다

## 2. 결정: 여러 겹
| 겹 | 기술 | 로그인 필요? | 언제 |
|---|---|---|---|
| 1 토큰 | 사용자 데이터 API + 장소·숙소 검색에 Bearer 요구 | 익명 계정이면 됨 | **TASK-012** |
| 2 Google 쪽 안전장치 | Google Cloud **예산 알림**(Billing → Budgets) + API 할당량(분·일). **상한은 넉넉하게**(멈추는 일 없게), 알림으로 이상한 사용량을 먼저 안다 | 아니오 | **지금** (결정권자 설정) |
| 3 한 번에 조금만 | 검색 결과 상한(10개), "전체 목록" API 만들지 않음 | — | 이미 됨 |
| 4 사용자별 할당량 | 계정별 하루 호출 수를 Redis(또는 DB)에 세고 넘으면 429. **새 익명 계정은 낮게** | 익명 계정이면 됨 | 파일럿 전 |
| 5 IP·기기별 횟수 제한 | 서버 앞 **Cloudflare** 규칙 + FastAPI 제한 도구(slowapi 등) + Redis | 아니오 | 파일럿 전 (서버 배포·도메인과 함께) |
| 6 익명 로그인 캡차 | **Cloudflare Turnstile** 또는 hCaptcha (Supabase 기본 지원) | 아니오 | 파일럿 전 (ADR-016 묶음) |
| 7 이상 감지 | **규칙 + 알림**: 계정·IP별 호출 수가 기준을 넘으면 알림, 사람이 판단. 하루 한 번 조회로 시작 | 아니오 | 파일럿 전 |
| 8 이용약관 | "자동으로 데이터를 수집하지 않는다" (법적 근거) | — | 파일럿 전 |
| 9 진짜 앱 확인 | iOS **App Attest** · Android **Play Integrity** (Firebase App Check로 묶음). 가장 강한 방법. 네이티브 모듈 → 앱 다시 설치 | 아니오 | **공개 출시 전** |

### 2-1. 막혀도 멈추지 않게
Google이 상한·오류로 안 되면 **앱은 계속 돈다**: 영업시간은 "미확인/모름"(TASK-010 §11 H4), 숙소 검색은 "지금 못 해" + 건너뛰기. 할당량에 걸린 계정만 자기 몫이 멈추고 다른 사용자는 영향 없다

### 2-2. 감시 에이전트는 나중
- 파일럿 전에는 **규칙 + 알림**만 (규칙으로 되는 건 규칙)
- R2 이후 실험 후보: 규칙이 걸러 낸 수상한 기록을 LLM이 읽고 **설명·대응안**을 정리. **차단은 자동으로 하지 않고 사람이 승인** (잘못 막으면 진짜 사용자가 피해 — "자동으로 일정을 바꾸지 않는다"와 같은 원칙). ADR-012의 정해진 순서 + 제한된 판단

## 3. 결과
- (+) 비용·긁어 가기를 여러 겹으로 줄이고, 최악에도 서비스는 멈추지 않는다
- (+) 대부분 사용자에게 안 보인다(앱 확인·IP 제한·할당량)
- (−) 새로 생기는 것: Redis, Cloudflare, Firebase App Check(출시 전, 앱 다시 설치)
- 남는 위험: 공개된 앱의 데이터를 완전히 막을 수는 없다 → 가치는 목록이 아니라 계획·코스 계산 기능에 둔다

## 포트폴리오 포인트
- "토큰이면 안전하다"에서 멈추지 않고, 익명 계정의 한계(IP 바꾸기)를 인정한 뒤 **비용 공격·긁어 가기·상한이 공격 수단이 되는 문제**를 여러 겹으로 설계
- 막혀도 멈추지 않는 동작 낮추기(NFR-12)를 보안에도 연결

| 예상 면접 질문 | 답 |
|---|---|
| "익명 로그인이면 남용은 어떻게 막나요?" | 토큰만으로는 못 막는다. 계정별 할당량(새 익명 계정은 낮게), IP 제한, 캡차, 출시 전엔 진짜 앱 확인(App Attest·Play Integrity)까지 겹으로 막고, Google이 막혀도 앱은 '미확인'으로 계속 돌게 했다 |
| "전체 비용 상한을 걸면 되지 않나요?" | 상한이 차면 진짜 사용자도 멈춘다. 그래서 전체 상한은 넉넉한 마지막 안전장치로 두고, 계정별 할당량으로 남용한 계정만 멈추게 했다 |
