# ADR-018 · 장소 늘리기: 수집 에이전트 + 평가 에이전트, Google은 "ID 받기와 쓰는 순간"에만

| 항목 | 내용 |
|---|---|
| 상태 | **초안 v1.1** — 결정권자 방향 승인 11-14 (구조·순서). **v1.1: 평가를 "통과/반려 문지기"에서 "점수·태그 층 + 최소 문지기"로** (결정권자 11-14). 세부 값은 TASK-016에서 |
| 관련 | ADR-015(장소 데이터 출처, **§3-3 Serper 범위를 이 ADR이 넓힌다**) · ADR-012(에이전트: 정해진 순서 + 제한된 판단, 출처 정책) · ADR-017(비용 상한) · DATA-001 B(places·place_facts) · `docs/data/osaka-seed.yaml` · CLAUDE.md 원칙 2(LLM은 사실 값을 만들지 않음) |

## 1. 문제
오사카 장소는 **58곳**(사람이 고르고 우리 값을 붙임). 기능 확인에는 충분했지만 실제 여행엔 적다 — 특히 식당은 동네마다 선택지가 적어 코스가 반복된다. 사람이 하나씩 늘리면 느리다(우리 값: 머무는 시간·혼잡·가격·분위기·지역을 사람이 정해야 함).

## 2. 선택지
| 안 | 장점 | 단점 |
|---|---|---|
| A. 사람이 계속 손으로 | 품질 확실 | 느림 (200~300곳 목표면 며칠~몇 주) |
| B. Google Places로 대량 수집 + 평점·리뷰로 자동 판단 | 빠름 | **약관 위반**(아래 §4): 지도 정보로 판단·파생물 금지, 캐시 금지 |
| **C. 수집·평가 에이전트 + 공개 자료 + 우리 기준, Google은 ID와 쓰는 순간에만** | 빠르고 약관 안 | 평가 품질을 증명해야 함, Serper 위험(§5) |

## 3. 결정: C
| 단계 | 누가·무엇으로 | 남기는 것 |
|---|---|---|
| ① 수집 | **수집 에이전트**: Serper 검색 결과, 가게 공식 사이트, 관광청 자료(오사카 관광국·JNTO 등)에서 동네·종류별로 **넓게** | 후보 이름·근거 링크 (원문 저장 안 함) |
| ② 최소 문지기 | 규칙 + 평가 에이전트: **폐업·위치 엉뚱함·지역 밖·중복·안전 문제**만 뺀다 (점수로 해결하면 안 되는 것) | 뺀 이유 |
| ③ 평가 층 | **평가 에이전트**: 공개 자료 + 우리 기준으로 **추천 점수 + 특징 태그**(정해진 목록에서만 고름, 예: 현지인 맛집·조용함·관광객 많음·사진 잘 나옴·줄 김) + 우리 값 초안 + **우리 말로 쓴 이유** + 평소 영업시간(공식 사이트 등, `unverified`) | 점수·태그·이유·우리 값 |
| ④ 검증 | **정답지**로 "좋은 곳이 위에 오는가"(순위 품질)와 태그 일치를 잰다. 정답지 = 결정권자가 확인한 장소, **좋은 곳 + 별로인 곳, 유명한 곳 + 덜 알려진 곳**을 섞는다(좋은 곳만이면 걸러 내는 힘을 못 잰다). 기준을 넘으면 **평소엔 믿는다**. **다시 검증하는 때**(정답지로 자동): AI 모델이 바뀜 · 지시문·기준을 고침 · 처음 보는 도시·종류 · 자료 모양이 바뀜. 가볍게: 수집 한 번마다 몇 곳(가설 5%)만 사람이 훑음 (결정권자 11-14) | 검증 기록(언제·어느 모델·어느 기준) |
| ⑤ 등록·사용 | Places API로 **장소 ID**만 받아 저장. 계획 엔진이 후보를 고를 때 **점수·태그로 순위**, 취향이 쌓이면 사람마다 다르게(RESEARCH-003 취향 기억). 쓰는 순간 Google에서 불러와 메모리에만(좌표 30일) | 장소 ID + 우리 한국어 이름 + 우리 값 + 점수·태그 + 평소 영업시간 |
- **왜 점수·태그 층인가**: 버리는 정보가 없다(기준이 바뀌면 다시 수집하지 않고 점수만 다시 봄) · 평가가 틀려도 "탈락"이 아니라 "순위가 조금 낮음" · 태그로 취향별 순위가 가능 · 검증이 "맞혔나"에서 "좋은 곳이 위에 오나"로 바뀌어 덜 깨지기 쉽다
- 점수·태그도 **Google 지도 정보로 만들지 않는다**(§4). 태그는 자유 글이 아니라 **정해진 목록** — 테스트할 수 있고 화면에 일관되게 쓸 수 있다
- 에이전트는 ADR-012 방식: **정해진 순서 + 제한된 판단**. 평가 에이전트는 수집 에이전트와 **다른 근거**(규칙 검사 + 다른 출처)로 본다 — 같은 모델이 같은 근거로 보면 같은 실수를 놓친다
- 사람 확인이 필요한 경우: 근거가 너무 적음(작은 가게 — 첫 수집에서 비율을 재 본다), 우리 기준과 크게 어긋남, 검증에서 순위가 자주 틀리는 종류
- 머무는 시간 같은 우리 값은 정답지로 다 못 잰다 → 나중에 실제 사용 기록(영업 확인·늦어짐)으로 다시 본다
- 목표량(가설): 오사카 200~300곳, 식당 비중 높게. 한 번 수집에 쓰는 **비용 상한**(Serper·LLM·Places ID 호출)을 미리 정한다 (ADR-017)

### 3-1. 영업시간 두 겹
| 언제 | 무엇으로 |
|---|---|
| 후보 고를 때 | **우리가 모은 평소 영업시간** (빠르고 Google 호출 없음) |
| 코스 확정 때 | 고른 장소만 Google로 확인, 다르면 Google 값을 믿고 코스를 맞춤 |
| 여행 당일 아침 (출발 전 점검) | Google로 다시 — 7일 안이라 임시 휴무·특별 영업시간까지. 닫혔으면 출발 전에 대안 카드 (TASK-017 알림과 함께) |
| 여행 중 | 지금처럼 1시간에 한 번 Google |
| 인터넷 없음 | 우리가 모은 평소 영업시간 + "미확인" |
- 영업시간은 **사실** 값이라 공식 사이트 등에서 우리가 모은 것은 저장해도 된다. **Google에서 받은 값은 평소 영업시간이라도 저장하지 않는다**

## 4. Google 약관 (원문 확인 11-14)
| 조항 | 뜻 | 우리 설계 |
|---|---|---|
| Terms 3.2.3(a) 긁기 금지 | 미리 받아 저장(pre-fetch)·색인·상호명·주소·리뷰 복사 저장 금지 | Google 값을 미리 받아 두지 않음. 이름은 우리 한국어 이름 |
| 3.2.3(b) 캐시 금지 | Service Specific Terms가 허용한 것만 캐시 | 장소 ID(무기한), 좌표(30일)만. **우리 서버·사용자 폰 모두** |
| 3.2.3(c) 파생 콘텐츠 금지 | Google 지도 정보로 콘텐츠를 만들지 않음. 예시에 **AI 모델 검증(validate)에 쓰기**까지 포함 | **평가에 Google 지도 API 정보(평점·리뷰·설명)를 쓰지 않음** — 내부 DB만이라도. "공개하느냐"가 아니라 "어떻게 쓰느냐"를 금지 |
| Places 좌표 30일 | 30일 뒤 삭제. 갱신으로 기간이 다시 시작되는지는 적혀 있지 않음 | **보수적으로**: 30일마다 지우고 필요할 때 다시 받음 |
- 쓰는 순간 불러와 사용자에게 보여 주고(출처 표시) 저장하지 않는 것은 허용 — 영업 중 확인·폐업이면 그때 화면에서 뺌
- 기준은 "들키느냐"가 아니라 "계약을 지키느냐". 어기면 API 키 정지 → 지도·영업시간이 통째로 멈춘다

## 5. Serper 범위 (ADR-015 §3-3을 넓힘)
- 전: ①개발 중 사람이 참고 ②빈 영업시간 보완(만들 때 한 번)
- 후: ① 범위에 **수집 에이전트의 후보 탐색**을 더함. 규칙은 그대로 — 결과 원문·요약·리뷰를 저장하지 않고, 후보 이름·근거 링크·**사실 값(영업시간)**만, 상태 `unverified`
- 위험: Serper는 Google 검색 결과를 대신 긁는 서비스(Google v. SerpApi, 2025-12). 사람이 참고하던 것을 에이전트가 대량으로 하므로 위험이 커진다 → **포트폴리오 수준에서 감수**(결정권자 11-09 "문제 생길 수 있을 때 알려만"). 앱 사용자 요청마다 실시간 호출은 여전히 하지 않음. 공개 출시 전 다시 판단

## 6. 결과
- (+) 장소를 늘리는 일이 "하나씩 손으로"에서 "검토하고 승인"으로
- (+) 약관 조항별로 근거를 남긴 설계 — 키 정지 위험 없이
- (+) 후보 고를 때 Google 호출이 줄어 비용↓, 오프라인에서도 평소 영업시간을 보여 줌
- (−) 평가 품질은 정답지 일치율로 계속 재야 한다 · Serper 위험 · 우리가 모은 영업시간은 오래되면 틀림(확정·당일 Google 확인으로 보완)

## 포트폴리오 포인트
- 약관을 조항 단위로 읽고 "내부 DB라도 안 되는 것"(파생·AI 검증)과 "되는 것"(ID·쓰는 순간)을 나눠 파이프라인을 설계
- 평가를 "통과/반려 문지기"가 아니라 **점수·태그 층 + 최소 문지기**로 설계 — 정보를 버리지 않고, 틀려도 덜 아프고, 취향별 순위로 이어짐
- 평가 품질을 주장이 아니라 **정답지(좋은 곳 + 별로인 곳)로 순위 품질**을 재서 증명하고, 바뀌는 순간에만 다시 검증

| 예상 면접 질문 | 답 |
|---|---|
| "장소 데이터를 AI로 모았다면서 Google 약관은요?" | Google 지도 정보로 판단하거나 저장하는 건 내부라도 금지라, 평가는 공개 자료와 우리 기준으로 하고 Google은 장소 ID 받기와 사용자에게 보여 주는 순간에만 썼습니다 |
| "AI 평가를 어떻게 믿었나요?" | 사람이 확인한 정답지와 일치율을 재서 기준을 넘으면 평소엔 믿고, 모델·기준·지역이 바뀌는 순간에만 정답지로 다시 검증했습니다(회귀 테스트처럼). 평가 에이전트는 수집 에이전트와 다른 근거로 보게 해 같은 실수를 놓치지 않게 했습니다 |
