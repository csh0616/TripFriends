## 4-0. 개발 진행 방식 (10-30 결정)
```
지금        PoC (Jev가 되는가)  ‖  요구사항 근거 조사 (REQ-001, 결정권자 직접)
              ↓ 결과로 Jev 범위 결정
11월        요구사항 분석 → 명세 (+ 완료 기준 = 테스트 기준)
            설계 (아키텍처, 데이터, 화면)
11~12월     R1 반복: 작업 지시서 → 테스트 먼저 → 구현 → PR 검토(+학습) → CI → 통합 → 기록
1월         R2 반복: 같은 순서로 Jev 융합
2월         확인: 파일럿 (실제 사용자)
3월         정리: 포트폴리오, 자소서
```
- **점진적으로**: 전체를 한 번에 하지 않고 R1, R2처럼 작은 단위로 명세 → 설계 → 구현 → 테스트를 반복한다
- **테스트 기준은 명세할 때**: 완료 기준(Given/When/Then)을 명세와 함께 쓴다 (V-모델)
- **통합·문서화는 매번**: PR이 합쳐질 때마다 CI와 기록. 마지막에 몰아서 하지 않는다
- **학습은 PR 검토 안에서**: "이 코드가 뭘 하는지 설명할 수 있나"를 검토 항목에 넣고, 모르는 건 LEARN-002로
- **검증과 확인**: 검증(명세대로 만들었나)은 테스트로, 확인(맞는 걸 만들었나)은 파일럿과 실제 사용자로

## 4-1. 테스트 먼저 (TDD) 규칙 (11-02 개정)
**대상**: 틀리면 안 되고 입력·출력이 분명한 곳 — 코스 계산(DP·탐욕법), 늦어짐 재조합 규칙, 가드레일, 안전 규칙, 대화/요청 라우터, 감지기. 화면, 연결 코드, 실험 스크립트는 일반 방식.

**순서**
1. **완료 기준**은 SRS-001 §5의 Given/When/Then에서 가져온다 (사람이 정한 기준)
2. **테스트 작성 에이전트**(Claude Code, 코드 작성과 다른 세션)가 완료 기준으로 테스트를 먼저 쓴다. 테스트 이름에 AC 번호를 붙인다 (예: `test_AC05_늦어짐_고정일정_유지`)
3. 자동화 도구로 테스트 자체를 보강한다
   - **속성 기반 테스트 (Hypothesis)**: 무작위 입력 수백 개로 불변식 확인. 예: "어떤 입력이든 코스는 영업시간·고정 일정을 어기지 않는다"
   - 경계값 자동 생성: 빈 후보, 후보 15개, 자정 넘김, 이동 시간 0
4. Claude가 테스트를 **한국어 요약표**(무엇을 확인하나, 왜 필요한가, 빠질 수 있는 경우)로 정리 → **결정권자가 읽고 이해한 뒤 승인**. 이해 안 되는 테스트는 LEARN-002로
5. **코드 작성 에이전트**가 테스트를 통과시킨다. 테스트를 고치려면 이유를 PR에 쓰고 결정권자 승인
6. 통과 후 **돌연변이 테스트 (mutmut)**: 코드를 일부러 망가뜨려 테스트가 잡는지 점수로 확인. 낮으면 테스트 보강
7. CI: 테스트, 커버리지, 타입 검사, 돌연변이 점수(핵심 모듈)

**이유**: 같은 AI가 테스트와 코드를 함께 쓰면 테스트를 코드에 맞춰 버릴 위험이 있다. 그래서 ① 기준은 사람이 정한 SRS에서, ② 테스트와 코드는 다른 세션이, ③ 테스트의 품질은 돌연변이 점수로 **숫자로 확인**한다.

**도구** (11-03 확정)
| 위치 | 예시 테스트 | 속성 테스트 | 돌연변이 |
|---|---|---|---|
| 서버 (Python) | pytest + coverage | Hypothesis | mutmut (엔진·`compose_screen`, 목표 80%) |
| 앱 (TS) | Jest(`jest-expo`) + React Native Testing Library | fast-check | Stryker (카드 그리기 규칙 등 핵심 로직만) |
| E2E | R1 후반 결정 (Maestro 후보) | — | — |
- 원칙은 양쪽이 같다: 예시 테스트 + 속성 테스트 + 돌연변이 점수. **비중은 서버가 크다** (판단·계산이 서버에 있으므로)

## 4-2. 검토 등급 (11-02)
| 등급 | 대상 | 방식 |
|---|---|---|
| **먼저 (막음)** | §4-1 대상의 테스트 요약표 | 결정권자가 이해하고 승인해야 코드 작성. 건당 5~10분 |
| **나중에 몰아서 (안 막음)** | 화면, API 연결, 설정, 문서, 리팩토링 | PM이 먼저 검토해 합치고 **미검토 목록**에 쌓음. 결정권자가 주 1회 몰아서 확인(학습 시간 겸함) |

- 미검토 목록: PR 번호, 내용 한 줄, PM 검토 메모, 결정권자 확인 날짜
- 주간 확인 때 이해 안 되는 코드는 LEARN-002로, 고칠 것은 리팩토링 목록으로

## 4. 일하는 순서
```
PM: 작업 지시서 작성 (범위, 완료 기준 Given/When/Then, 건드릴 폴더)
  → 팀 에이전트: 브랜치에서 테스트 먼저(§4-1 대상) → 결정권자 테스트 검토 → 개발
  → PR 올림 (무엇을, 왜, 테스트 결과)
  → CI 자동 검사 (타입, 테스트, 린트)
  → PM 검토: 완료 기준, 원칙, 계약 위반 여부
  → 결정권자 최종 승인 → 합치기
  → PM: 결정 기록, 포트폴리오 숫자 기록, 학습지원에 배울 포인트 전달
```

## 포트폴리오 포인트
- **보여주는 것**: AI 에이전트 팀을 설계하고 운영한 경험. 계약 관리, 완료 기준, 검토 흐름
- **흔한 방식과 차이**: AI에게 "만들어 줘"가 아니라, 팀 경계·계약·완료 기준을 정하고 검토하는 구조로 운영했다

### 예상 면접 질문과 답
| 질문 | 답의 뼈대 |
|---|---|
| 이 코드 직접 짰나요? | 팀 에이전트가 작성하고, 나는 범위·계약·완료 기준을 정하고 PR을 검토·승인했다. 핵심 로직(조합, 코스 계산)은 직접 설명할 수 있다 (예: DP가 왜 최적인지) |
| 에이전트끼리 충돌은 어떻게 막았나? | 팀은 자기 폴더만 고치고, 같이 쓰는 계약(카드 스키마, API 타입)은 PM 승인으로만 바꿨다. CI가 타입 불일치를 잡는다 |
| AI가 만든 코드 품질은 어떻게 보장했나? | 완료 기준을 테스트로 만들고, CI와 PR 검토를 거쳤다. 통과율과 결함 수를 기록했다 (값으로 채움) |
