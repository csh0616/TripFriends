## A. 감지 규칙 (순수 함수, `apps/server/trip/detect.py`, TDD)
`detect_delay(course, at, position) -> DelayFinding | None`
| 단계 | 규칙 |
|---|---|
| A1 어디 있나 | `position`에서 **150m 안**의 코스 장소 중 가장 가까운 곳 = `at_place`(순번 k). 없으면 `None` (이동 중은 이번에 판단 안 함) |
| A2 얼마나 늦었나 | k의 예정 출발 시각 `leave_k` = (k+1번 시작 − 이동 분). `at > leave_k`면 `delay_min = at − leave_k` (분, 내림). k가 마지막이면 `None` (지킬 다음 일정이 없음) |
| A3 문턱 | `delay_min < 10` → `None` |
| A4 심각도 | **높음**: `delay_min ≥ 20` **또는** 일정을 `delay_min`만큼 미뤘을 때 남은 고정 일정 중 하나라도 시작에 늦음. 그 밖 **낮음** |
| A5 `dedupe_key` | `"delay:{day_id}:{k}"` (같은 장소에서 늦어진 건 한 사건) |

## B. G2 그래프와 API (`backend`)
### B-1. 그래프 (LangGraph, R1 규칙 노드만, `apps/server/graphs/trip.py`)
| 지금 | 이벤트 | 처리 | 다음 |
|---|---|---|---|
| (없음) | check, 감지 없음 | — | (없음) |
| (없음) | check, **낮음** | 사건 저장(`open`, 제안 없음) | `open_low` |
| (없음) | check, **높음** | 사건 저장 → §B-2 대안 계산 → 제안 저장 → **interrupt** | `awaiting` |
| `open_low` | check, 같은 키·여전히 낮음 | 증거(`delay_min`)만 갱신, 알림 없음 | `open_low` |
| `open_low` | check, 같은 키·**높음으로** | 대안 계산 → interrupt (사건당 한 번) | `awaiting` |
| `awaiting` | check, 같은 키 | 증거만 갱신. 제안은 그대로 (다시 알리지 않음, AC-10) | `awaiting` |
| `awaiting` | `accept{proposal_id}` | 그 안을 일정에 반영 (§B-3) | `resolved` |
| `awaiting` | `dismiss` | 일정 그대로 | `resolved` |
| `resolved` | check, 같은 키 | 아무것도 안 함 (같은 사건 다시 안 알림) | `resolved` |
| 그 외 | 아무 이벤트 | 409 `STATE_CONFLICT`, 그대로 | 그대로 |
- 스레드 ID = 사건 ID. 체크포인터는 TASK-003과 같은 `MemorySaver`
- **TASK-003 R1·R12 교훈 그대로**: 줄 함수는 계산 → 응답 → 저장 순서, 노드 안 예외는 잡아서 같은 interrupt 자리로 돌아온다 (§6)
- 다른 장소(k가 바뀜)에서 늦어지면 **새 사건** (키가 다름)

### B-2. 대안 계산 (사건 "높음"일 때)
- 입력: 남은 장소 = k+1번부터의 코스 항목, 출발 = `at`·k번 위치, 고정 일정·꼭 갈 곳은 **지킨다**, 하루 끝·숙소 그대로
- `compose_courses`를 그대로 써서 **relaxed·packed 두 안**을 얻는다. 두 안이 같으면 하나만
- 제안마다 `summary`: 빠지는 곳 이름들, 고정 일정 시작에 맞는지, 바뀐 첫 출발 시각. `reason`(대본):
  - 빠지는 곳 있음: "{이름들} 빼고 {고정 일정 제목}에 여유 있게" (고정 일정 없으면 "… 빼고 남은 일정 여유 있게")
  - 빠지는 곳 없음: "머무는 시간 줄여서 다 가기"
- `Infeasible`(고정 일정을 어떻게 해도 못 지킴) → 제안 0개, 사건 `awaiting`, 카드에 "어떻게 해도 {제목}에 늦어" + [그대로]만
- DP 상한(TASK-005 12곳)은 그대로 적용

### B-3. 반영 (accept)
- 고른 코스의 **k번까지(지난 것)는 그대로**, k+1번부터를 제안 안으로 바꾼 **새 코스안**을 만들어 그날의 선택으로 저장 (옛 안은 남김, 기록용)
- 반영 뒤 NowView는 새 코스 기준. 사건 `resolved`, `user_choice=accepted`

### B-4. API
| 메서드·경로 | 요청 | 성공 | 실패 |
|---|---|---|---|
| POST `/days/{day_id}/check` | 본문 `{at, lat, lng}` (**위치는 본문**, 저장 안 함, 로그에 안 남음) | 200 `NowView` + `event` | 400, 404(`day`/`course`) |
| POST `/proposals/{proposal_id}/accept` | — | 200 `NowView` (새 코스) | 404 `proposal`, 409(이미 처리됨·오래됨) |
| POST `/events/{event_id}/dismiss` | — | 200 `NowView` | 404 `event`, 409 |
- `GET /now`는 그대로 두되 **위치 쿼리는 받지 않는다**(무시) → 앱의 위치는 `check`로만 (TASK-006 Q9 해결)
- 제안이 **오래됨**: 제안을 만든 뒤 `at`이 **15분 이상** 지났거나 같은 사건의 `delay_min`이 **10분 이상** 늘었으면 accept는 409 `STATE_CONFLICT`(`detail.reason="stale"`). 앱은 check를 다시 불러 새 제안을 받는다. 이때 같은 사건의 제안을 **한 번 새로 계산**하고 다시 알리지는 않는다(카드만 갱신)

### B-5. NowView에 더하는 것
```json
"event": null | { "event_id", "type": "delay", "severity": "low|high", "delay_min": 23,
  "state": "open_low|awaiting|resolved",
  "proposals": [ { "proposal_id", "label": "relaxed|packed", "reason": "…",
                   "dropped": [ {"place_id","name"} ], "keeps_fixed": true,
                   "first_leave_at": "13:40", "items": [NowCourseItem] } ] }
```
- `status` = 사건이 `open_low`·`awaiting`면 `delayed`, `status_text` = "**{delay_min}분 늦어지는 중**"
- `compose_screen` 입력 `open_events` = `awaiting` 사건 (순위 3 → 메인 **T-04**). `open_low`는 카드 안 바꿈, 알약만
- **T-04 카드**: `{type:"T-04", event_id, delay_min, proposals[], fixed: {title,start}|null}`. 지원 카드 목록에 T-04 추가 (TASK-006 A3)
- 짝(§5): T-04 → T-07(고정 일정 있으면), T-03

## 10. 학습 카드 (결정권자용)
1. **지도**: check(지금 어디·몇 시) → 감지 규칙 → 사건 → (높으면) 대안 계산 → **멈춰서 기다림(interrupt)** → 사용자가 [이걸로]/[그대로] → 반영 또는 그대로
2. **핵심 개념**: 사건의 중복 제거(`dedupe_key`) · "화면이 바뀌는 것 ≠ 일정이 바뀌는 것" · 오래된 제안(stale) 처리
3. **직접 해보기**: 데모에서 [+10분 늦게]를 한 번(10분: 낮음, 알약만) → 두 번(20분: 높음, 카드)
4. **내 말로**: "왜 대안을 자동으로 적용하지 않나?" / "같은 늦어짐을 왜 한 번만 알리나?"
