## A. 숙소 입력 세 단계 (결정권자 11-15)
지금: Google 실시간 검색 `includedType: lodging` → 숙소 종류로 등록된 곳만 나온다. **에어비앤비·지인 집·작은 숙소는 못 찾는다**

| 단계 | 사용자가 하는 일 | 서버 | 남기는 것 |
|---|---|---|---|
| ① 이름 | 검색창 하나에 숙소 이름 (지금과 같음) | 지금 `lodging-search` | 장소 ID |
| ② 주소 | ①에서 못 찾으면 **같은 글을 주소로 다시** 찾기 — 사용자가 다시 치지 않는다. 일본어·영어 주소 | 주소 검색(Google, 종류 제한 없이) | 장소 ID(있으면) + **입력한 주소 글자**(사용자 데이터) |
| ③ 지도 찍기 | 그래도 안 되면 지도에서 대략 그 동네를 길게 눌러 핀 | Google 호출 없음 | **사용자가 찍은 좌표** + 사용자 이름표(선택, 예 "친구 집") |
- 계획엔 "대략 어느 동네"면 충분하다 — 에어비앤비는 예약 전 정확한 주소를 안 보여 준다. ③ 화면에 "대략이어도 괜찮아" 한 줄
- **약관·저장 규칙** (ADR-015·018)
  - Google이 준 좌표는 지금처럼 30일 규칙(저장 안 함 또는 30일 안 삭제), 이름·주소 문구도 Google 것은 저장하지 않는다
  - **사용자가 직접 친 주소 글자와 지도에서 찍은 좌표는 사용자 데이터** — Google 콘텐츠가 아니므로 여행 데이터로 저장한다. 실시간 위치 규칙(TASK-014: 좌표 저장 0)과 다르다: 이것은 "지금 어디 있나"가 아니라 계획의 출발점이다 → **저장 (결정권자 11-16, Q1)**
  - 숙소는 우리 장소 DB(`places`)에 넣지 않는다. 여행마다 `trip.lodging`에만
- **데이터 모양** (test-writer가 제안 → PM 승인): `trip.lodging = {kind: "place"|"address"|"pin", place_id?, address_text?, lat?, lng?, label?}` 또는 `null`. `kind: pin`만 서버가 좌표를 그대로 가진다. `place`·`address`는 쓰는 순간 장소 ID로 불러온다
- API-001: `POST /trips`의 `lodging_place_id?` → `lodging?`(위 모양). 옛 필드는 요청에서만 받기(앱이 바로 바뀌므로 짧게). PM이 고친다. (v1.0의 `PATCH /trips/{id}`는 **없는 길을 잘못 적은 것** — §9 Q3)
- 엔진: 숙소 좌표를 쓰는 곳(하루 첫·마지막 이동, T-08 "숙소 가는 길", 지도 집 표시, 카메라)이 세 종류 모두에서 같은 값을 받는지. `kind: pin`의 T-08 길 안내는 좌표로 연다
- 실패: 주소 검색 공급자 실패 → 503 `PROVIDER_UNAVAILABLE`, 앱은 "지금 주소로 못 찾았어" + **바로 ③ 지도 찍기로** 갈 수 있게(막히지 않게)

## 포트폴리오 포인트
- 숙소 검색을 "못 찾으면 끝"이 아니라 **이름 → 주소 → 지도 찍기**로 내려가게 설계 — 실제 사용자(에어비앤비·지인 집)의 막힘을 폰 확인에서 찾아 풂
