## T. 테스트용 DB
- 테스트는 **실제 Supabase 클라우드에 붙지 않는다**. 로컬 Postgres(Docker 또는 Supabase CLI `supabase start`)에 붙는다
- 메인 세션이 먼저 `docker`·`supabase` 명령이 있는지 확인. 없으면 설치 방법 2가지(Docker Desktop / OrbStack)와 크기를 결정권자에게 보고하고 기다린다
- DB 테스트는 표시(`db`)를 달아, DB가 없으면 건너뛰고 이유를 한 줄 출력

## B. 1단계 — 익명 계정 (서버·앱)
| # | 할 것 |
|---|---|
| B1 | 앱을 처음 열면 **익명 로그인**(Supabase Auth). 사용자에게 화면 없음. 세션은 기기에 저장 |
| B2 | 앱 → 서버 요청에 `Authorization: Bearer <JWT>`. 서버는 JWT를 확인해 `user_id`로 구분. **`X-Device-Id` 대체** |

## 포트폴리오 포인트
- 저장소 인터페이스 하나에 메모리·Postgres 두 구현, **같은 계약 테스트**로 바꿔 끼움을 증명
- "실패한 요청은 아무것도 바꾸지 않는다"를 메모리에서 DB 트랜잭션까지 이어서 보장 (TASK-003 R12의 남은 한계 해결)
- 익명 → 계정 연결에서 데이터가 사라지는 경우를 규칙·테스트로 먼저 막음 (ADR-016)

| 예상 면접 질문 | 답 |
|---|---|
| "메모리 저장소에서 DB로 어떻게 옮겼나요?" | 처음부터 저장소 인터페이스를 두고 메모리 구현으로 시작했다. DB 구현을 더하고 같은 계약 테스트를 두 구현에 돌려 동작이 같음을 확인했다 |
| "저장 중에 실패하면?" | 요청 하나를 트랜잭션 하나로 묶었다. 테스트에서 일부러 중간에 예외를 내 DB가 요청 전과 같은지 확인했다 |
