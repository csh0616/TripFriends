## 2. 화면 틀 (SC-04) — 지도 + 카드 시트 (11-02 결정권자 제안으로 변경)
```
┌────────────────────────────┐
│ [프로필] [이동 상태 알약] [SOS] │  ← 지도 위에 떠 있음, 위치 고정
│                            │
│   지도: 오늘 동선(지난 길 회색, │  ← 내 위치(앱 켜진 동안만, 기기 표시만)
│   남은 길 점선), 장소 번호 핀   │     카드가 장소를 말하면 지도에도 핀
│                     [내 위치] │
├──── 카드 시트 (끌어서 3단) ────┤
│ 제안 칩 / 친구 한마디 (선택)    │
│ 메인 카드 1장                  │
│ 보조 카드 0~3장                │
│ 바뀐 이유 (작게)               │
├────────────────────────────┤
│ 고정: 입력창 [말하기]           │
└────────────────────────────┘
```
- **이동 상태 알약**: "동선대로 가는 중"(초록) / "20분 늦어지는 중"(주황) / "다음까지 여유 있음". 규칙이 정하고, 사용자가 "잘 가고 있나"를 한눈에 확인
- 시트 3단: 낮게(메인 한 줄) · 중간(메인+보조, 기본) · 높게(전체). 강한 신호가 오면 중간으로 올라옴
- 길 안내는 직접 만들지 않고 [길 안내] → 구글 지도 앱으로 넘김
- 지도와 카드는 같은 데이터: 대안을 고르면 지도 선도 바뀜 (늦어짐 화면)
- 오프라인이면 지도 대신 카드만 있는 화면 (X-02)
- 조합 영역(메인 + 보조)은 **최대 4장**, 읽는 순서: 상황 → 판단 → 행동 (PRD §4-3)
- 계획 대화(SC-02)는 지도 없이 고르기에 집중. 코스안 화면에만 작은 동선 지도

### 머무는 시간 (FR-07a)
| 종류 | 최소 · 보통 · 최대 (가설) |
|---|---|
| 카페 | 30 · 60 · 90분 |
| 식사 | 45 · 60 · 90분 |
| 산책·거리 | 30 · 60 · 120분 |
| 박물관·미술관 | 60 · 90 · 150분 |
| 큰 명소 | 60 · 120 · 180분 |
- 느긋하게: 보통~최대 쪽 + 장소 사이 15분 / 꽉 채워서: 최소~보통 쪽 + 5분 (가설)
- 코스안의 시간을 누르면 [−15분] [+15분]. 늘려서 빠지는 곳이 생기면 "이러면 ○○이 빠져" 확인 후 반영

### 4-2. 애매한 상황 → 규칙 (11-02 측정으로 변경)
> 측정 결과 Jev는 말이 없는 애매 상황에서 37.5%로 기각 (POC-001 §8). 아래 R2 Jev 보기 열은 **쓰지 않는다**. 대신 **강한 신호 규칙 + 제안 칩**(§4-2a)으로 처리한다
| 상황 예 | R1 규칙 기본값 | R2 Jev 보기 |
|---|---|---|
| 다음 일정까지 30~60분 여유 | T-01 | T-01 / T-11 / T-09 / T-10 |
| 비 예보 + 실외 일정이 남음 | T-01 | T-01 / T-12 |
| 점심·저녁 시간대인데 식사 일정 없음 | T-01 | T-01 / T-10 / T-11 |
| 오래 걸었음 (오후 늦게, 일정 많이 소화) | T-01 | T-01 / T-09 |

### 4-2a. 강한 신호 규칙과 제안 칩 (11-02 검증 반영)
새 상황 12개로 검증한 결과 "여유 시간 → 여유 시간 제안"은 7번 중 0번 맞아 삭제. 강한 신호만 메인으로 올리고, 약한 신호는 제안 칩으로 (POC-001 §8-5·8-6)

| 신호 | 조건 | 처리 |
|---|---|---|
| 강함 | 식사 시간대(11:30~13:30, 18:00~20:00) + 이번 끼니 안 먹음 + 다음 일정(식사 아님)까지 45분 이상 | 메인 T-10 |
| 강함 | 2시간 안 비 예보 60% 이상 + 실외 일정 남음 | 메인 T-12 |
| 강함 | 오늘 10km 이상 걸음 + 다음 일정까지 30분 이상 | 메인 T-09 |
| 강함 | 남은 일정 없음 + 18:00 이후 | 메인 T-08 |
| 약함 | 7~10km 걸음 (다음 일정까지 30분 이상) | 메인 T-01 그대로, 칩 **T-09** "근처 쉴 곳 볼래?" |
| 약함 | 식사 시간대 시작 30분 전 + 이번 끼니 안 먹음 | 메인 T-01 그대로, 칩 **T-10** "근처 먹을 곳 볼래?" |
| 약함 | 여유(이동 제외) 30분 이상 | 메인 T-01 그대로, 칩 **T-11** "근처 둘러볼 곳 볼래?" |
| 약함 | 남은 일정 없음 + 18:00 전 | 메인 T-01 그대로, 칩 **T-11** "근처 둘러볼 곳 볼래?" |
| 없음 | 그 외 | 메인 T-01 |

- 제안 칩은 한 번에 1개. 약한 신호가 여러 개면 **위 표 순서**(쉴 곳 → 먹을 곳 → 둘러볼 곳)로 첫 번째만 (11-03)
- 같은 칩은 30분 안에 다시 띄우지 않음 (가설)
- 칩을 누르면 해당 카드가 메인으로 (사용자의 요청과 같은 처리)

### 4-3. 사용자의 말 → R2 (ADR-011 A 다음 단계, **D-1 측정으로 Jev 확정**)
1. 안전 규칙 → X-01
2. Jev A: 대화 / 요청 (확신 0.6 미만 → T-14 되묻기)
3. 요청이면 Jev가 **메인 카드 1장**을 고른다. 보기: T-02 / T-03 / T-04(일정 바꿔 줘) / T-08 / T-09 / T-10 / T-11 / T-13
4. 대화면 카드는 그대로 두고 친구 한마디만 바꾼다 (말할 때마다 화면이 바뀌지 않게)
5. Jev가 0.8초 안에 답하지 않거나 확신이 0.6 미만이면 → T-14 되묻기 (ADR-011 운영 값)

### 4-4. 구현 중 정한 것 (TASK-001 1차, 11-03 결정권자 확인)
| 항목 | 결정 |
|---|---|
| 순위 7 "일정 끝" | §4-2a 기준: 남은 일정 없음 + 18:00 이후 → T-08 (강한 신호보다 앞, §4-1 자리). 18:00 전은 약한 신호 |
| 다음 일정이 없을 때 "다음 일정까지 N분 이상" | 참으로 본다 (제한 없음) |
| 이동 상태 알약 | 열린 늦어짐 사건 → `delayed` / 여유 30분 이상 또는 다음 일정 없음 → `free` / 그 외 `on_track` |
| 오프라인 화면 | 메인 T-01, 보조 순서 X-02 → T-02 → T-03 |

|---|---|
| 도착, 출발 (목적지 근처 판정이 바뀜) | 위치가 조금 바뀜 (같은 장소 안) |
| 새 사건 감지 (늦어짐, 닫힘, 날씨) | 같은 사건 재감지 (`dedupe_key`, AC-10) |
| 시간 경계 (출발 10분 전, 고정 일정 15분 전) | 사용자가 카드를 만지는 중 (마지막 조작 후 **30초** 안, 가설) |
| 사용자의 요청 (말, 버튼) | 직전 변경 후 **3분** 안의 규칙 순위 5~8 변경 (가설, 깜빡임 방지) |
| 안전·오프라인 (항상 즉시) | 대화로 판단된 말 (한마디만 바뀜) |

- 바꿀 때마다 **바뀐 이유 한 줄**을 보여 준다. 이유 문장은 규칙이 정한 틀(대본)이고 LLM이 쓰지 않는다
- 사용자가 고르기 전에는 **일정 자체는 바뀌지 않는다** (AC-06). 화면이 바뀌는 것과 일정이 바뀌는 것은 다르다

## 7. 역할 D 측정 계획 (gold_C)
| 항목 | 내용 |
|---|---|
| 질문 | 애매한 상황과 요청 문장에서 **메인 카드 1장**을 Jev가 규칙보다 잘 고르나? |
| 데이터 | 20개: 분명한 상황 5 (규칙 확인용, Jev 안 부름) · 애매한 상황 8 (§4-2) · 요청 문장 7 (§4-3) |
| 정답 | 다른 AI 두 개(Gemini + 하나 더)가 메인 카드를 고름. 둘이 갈리면 '경계'로 따로 봄. PM은 정답을 달지 않음 |
| 비교 | 규칙 기본값 vs Jev choice (보기 = §4-2·4-3의 카드 ID) |
| 채택 기준 (가설) | Jev 정확도 80% 이상 **그리고** 규칙 기본값보다 +15%p. p95 0.8초 이하 |
| 주의 | criteria는 고르기 보기로 쓴다 (score는 척도, POC-001 §7-3). 보기 설명은 카드 이름이 아니라 "이 카드가 보여 주는 것"으로 쓴다 |

## 포트폴리오 포인트
- **보여주는 것**: 화면을 "카드 카탈로그 + 고르는 규칙"으로 설계한 것. 분명한 상황은 우선순위 표(테스트 가능), 애매한 상황만 모델. 깜빡임을 막는 변경 규칙과 "바뀐 이유" 표시
- **프론트엔드 관점**: 서버가 고른 카드 ID와 값을 앱이 그리는 서버 주도 UI(Server-Driven UI). 카드 스키마 한 곳에서 타입 생성
- **에이전트 관점**: 모델은 한 장만 고르고, 나머지는 규칙. 실패하면 되묻기·기본값으로
- **예상 면접 질문**
  - "AI가 화면을 바꾸면 사용자가 혼란스럽지 않나요?" → "바꾸는 때를 사건·시간 경계·요청으로 제한하고, 조작 중엔 보류하고, 바뀔 때마다 이유 한 줄을 보여 줬다. 안전 버튼과 입력창 위치는 절대 안 바뀐다"
  - "왜 카드 여러 장을 모델이 고르지 않았나요?" → "여러 개 동시 판단은 정확 일치 45%로 측정됐다. 메인 한 장만 모델, 짝은 규칙으로 했다"
